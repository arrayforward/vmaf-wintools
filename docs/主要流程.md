# 主要流程

## 1. 评估主流程 (Pipeline)

```
开始
 │

打开参考视频 ────────────────────────────► 打开目标视频
 │                                          │
 ▼ 第一遍扫描                               ▼ 第一遍扫描

                │ 是
                ▼

                ▼

                ▼

                ▼

 │     │   (采样模式: 未采样, 直接跳过 │
 │     │    不计丢帧不打日志)          │
 │     │                             │
 │     ▼                             │
 │  目标解码器前进到匹配帧号            │
 │     │                             │
 │     ▼                             │
 │  两端裁剪 → 较大端降采样到比较分辨率 │
 │     │                             │
 │     ▼                             │
 │  vmaf_read_pictures 送帧           │
 │  查询上一帧分数 → 回调 onFrame      │

                ▼
        vmaf flush → 补齐全部帧分数
                ▼

```

关键约束:
- **参考帧必须逐帧读取**,即使该帧判定为丢帧——解码器是顺序的,跳过会导致后续全部错位(开发中实际踩过的坑)
- 丢帧帧对不送入 libvmaf,只统计
- VMAF 单帧分数在送入下一帧后才就绪(motion 特征需要下一帧),因此采用"延迟一帧"查询,flush 后补齐
- **采样模式**(目标为截图文件夹/image2 序列):只统计匹配帧对,未采到的参考帧不计丢帧(`Summary.dropped=0`)、不打逐帧日志;冻结统计保留;进度按匹配对数推进

## 2. 帧对齐子流程 (QR 帧号)

帧号标记规范见 帧号标记规范.md:片源每帧烧录 QR 帧号(marker_burn),端侧采集画面连同标记一起被录下。

```
第一遍扫描: 逐帧 decodeMarker → markerIndex[](-1 = 未识别)
            记录首个有效标记的 QR 外接框 (供自动裁剪)

对齐 (buildMarkerMapping):
  目标侧: 帧号 → 首次出现的帧位置 (哈希表);重复出现计入 freezeCount
  冻结段: 目标侧连续相同帧号 ≥2 帧 → freezeSegments++, 最长段 = freezeMaxLen
  参考侧: 逐帧按帧号查表
    查不到 → 丢帧 (droppedCount++)
    未识别 → 不映射 (refToDist = -1)
```

天然处理丢帧、冻结、乱序、帧率不一致,无需粗对齐/搜索窗口。

**自动裁剪**:QR 码在片源中的位置是已知的(烧录时相对源画面定位),因此由采集帧中 QR 的实测外接框(第一遍扫描对全部识别帧取均值)可反推出采集画面里视频区域的精确位置和缩放比例,两端各自裁剪出纯视频区域。反推失败(如标记被截断)则退回全帧。反推框存在 ±1px 量化误差,再用首个映射帧的实际内容做黑边吸附细化(纯黑边按内容边界精修,充满画面时直接贴边)。

**比较分辨率**:两端裁剪尺寸不一致时取较小者,较大端降采样后送 VMAF(libvmaf 按该尺寸初始化),避免把小尺寸采集帧上采样回源分辨率压低分数。注意 v0.6.1 模型按 1080p 观看条件校准,小分辨率比较下分数语义有偏差(绝对分仅供参考)。

## 3. VMAF 评分子流程 (VmafEvaluator)

```
vmaf_init(threads, subsample)
vmaf_model_load (内置名) 或 vmaf_model_load_from_path (json)
vmaf_use_features_from_model
循环: vmaf_picture_alloc → 填充 Y/U/V → vmaf_read_pictures(index) → unref
vmaf_read_pictures(NULL, NULL, 0)  // flush
vmaf_score_at_index(i)             // 逐帧
vmaf_score_pooled(MEAN/HARMONIC_MEAN/MIN/MAX)
vmaf_model_destroy / vmaf_close
```

## 4. 预处理流程 (PreprocessTab)

```
选择输入 → ffprobe 获取源分辨率/帧率/时长
   │
   ├─ 勾选绿屏:
   │   ffmpeg -i in -f lavfi -i color=green:s=WxH:r=FPS:d=5
   │   -filter_complex "[0:v]scale=W:H,fps=FPS[main];[1:v][main]concat=n=2:v=1[out]"
   │   -map "[out]" -c:v libx264 -b:v <码率> -pix_fmt yuv420p out.mp4
   │
   └─ 仅转码:
       ffmpeg -i in -vf scale=W:H -c:v libx264 -b:v <码率> -pix_fmt yuv420p out.mp4

进度: 解析 stderr 中 time=HH:MM:SS.xx, 按时长百分比更新进度条
```

要点:
- 绿屏段分辨率/帧率与源一致,保证 concat 顺利
- 绿屏从 GOP 起点开始编码,天然是关键帧边界
- 输出统一 yuv420p / H.264,兼容性最好

## 5. CLI 流程

`vmaf_tool --cli [参考视频] <目标视频或截图文件夹> [--model ...]`;参考视频可缺省,缺省时自动解析 `ai_game_1080p60.mp4`(搜索顺序:exe 同级 → exe/testdata/ → exe 上两级 testdata/)。另有独立命令行 `eval_cli <ref> <dist视频或截图文件夹> [model]`(帧号对齐 + 自动裁剪)。
与 GUI 共用同一 `Pipeline`,仅回调改为 stdout 打印,用于脚本化批量测试与回归验证。

## 6. 验证流程 (开发期)

| 用例 | 构造 | 预期 |
|---|---|---|
| 自比对 | ref vs ref (烧码后) | VMAF ≈ 99+,映射 1:1 |
| 帧号对齐 | marker_burn 烧码 + 丢 10% 帧 + 冻结 5% 帧 + 降 24fps | 逐帧映射 100% 正确,丢帧/冻结统计与合成真值一致 (tests/align_test) |
| 截图文件夹 | dist 导出 PNG 序列作为目标输入 | 采样模式:仅统计匹配帧对,未采样参考帧不计丢帧 |
| 无帧号标记 | 未烧码视频直接评估 | 明确报错"请使用 marker_burn 生成片源",不崩溃 |
| 端到端真机 | 真机本地播放烧码片源 + adb 截图采集 | QR 帧号识别率 100%、对齐正确率 100%;VMAF 绝对分受显示缩放滤波影响(竖屏 0.56x 显示下约 75 为测量上限),基准验证建议横屏或分辨率匹配的设备 |
